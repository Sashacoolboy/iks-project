# Ризики на Кроці 2: перегляд/вибір при виборі активів + режим ручного вводу загрози

**Дата:** 2026-09-17
**Статус:** Approved

## Мета

Зараз користувач бачить ризики, повʼязані з активами, лише на Кроці 3 (Ризики), уже
після того як усі активи обрано на Кроці 2. Це пізно: вибираючи активи, користувач не
розуміє, які загрози на них чекають, і не може одразу вирішити, які з них релевантні для
цієї ІКС.

Мета — перенести момент ознайомлення й первинного відбору ризиків на Крок 2 (Активи),
одразу біля щойно вибраного активу, залишивши Крок 3 місцем для подальшого редагування,
видалення й фіналізації переліку. Додатково — дати можливість вводити загрозу, якої немає
в довіднику (`data/threats_risks.json`), без примусового заповнення оцінки ризику одразу.

## Межі змін

- Схема `state.risks` не змінюється (`accepted_base`, `custom`, `base_overrides`,
  `hidden_base`) — значення `accepted_base` й далі визначає, які базові ризики
  потрапляють у роботу на Кроці 3, просто **керується тепер на Кроці 2**, а не
  автоматично при рендері Кроку 3 (як зробили минулою ітерацією).
- Крок 3 (`step3-base-risks.js`) не змінює таблицю/кнопки редагування-видалення.
  Єдина зміна в логіці рендера — прибирається блок «на кожному рендері `accepted_base`
  = всі видимі базові ризики» (доданий минулою ітерацією): тепер цей масив формує
  виключно Крок 2 через чекбокси, і Крок 3 просто читає його готовим.
- Спільний модал «Додати ризик» виноситься з `step3-base-risks.js` у окремий модуль
  `public/js/risk-form.js`, щоб його міг викликати і Крок 2, і Крок 3 без дублювання коду.
- `core/risk-engine.js`: `annotateRisk` толерантна до відсутніх `impact`/`likelihood`
  (ризик без оцінки) — адитивна зміна, не ламає існуючі виклики (усі базові й уже наявні
  кастомні ризики завжди мають обидва поля).
- Без змін у `server.js`, `core/template-io.js`, `core/docx/*`, DOCX-експорт ризиків.

## 1. Крок 2: панель «Ризики обраних активів»

`public/js/steps/step2-assets.js`, під списком категорій активів:

- Якщо `state.selected_assets` не порожній — рендериться секція
  `<div class="risk-preview">` з заголовком `Ризики обраних активів (N)`.
- Групування: `<fieldset>` на кожен обраний актив (у порядку вибору), у ньому —
  `baseRisksFor(catalog, [assetId], as_class)` для цього конкретного активу,
  відфільтрований від `hidden_base` (так само, як і зараз на Кроці 3 — раніше видалений
  ризик тут не зʼявляється), кожен рядок = `<label class="checkbox">` із чекбоксом,
  повʼязаним із `state.risks.accepted_base.includes(risk.id)`, і коротким описом
  (`threat` — `vulnerability`, бейдж рівня).
- Чекбокс on/off одразу оновлює `risks.accepted_base` (додає/прибирає id) через
  `setState`, без підтвердження (`confirm()`) — це не видалення, а лише позначка
  «включити в роботу на Кроці 3».
- Під переліком ризиків активу — кнопка `+ Додати свій ризик до цього активу`, яка
  відкриває спільний модал `openRiskFormModal` (див. розділ 2) із **вже підставленим**
  `assetId` цього активу (селект активу в модалі одразу вибраний, змінити можна).
- Якщо в активу немає жодного каталожного ризику — замість переліку рядок
  `Немає готових загроз у довіднику для цього активу.` (кнопка «Додати свій ризик»
  залишається).

Якщо жодного активу не вибрано — панель не рендериться (як і зараз для порожнього
`selected_assets`).

## 2. Спільний модал `public/js/risk-form.js`

Новий модуль, що інкапсулює обидва режими додавання ризику. Експортує:

```js
export function openRiskFormModal({ presetAssetId, onSaved } = {}) { … }
```

Внутрішня структура — перемикач режиму (два `button`-таби зверху модалу):

- **«З переліку»** (за замовчуванням) — теперішня логіка `openAddRiskModal` з
  `step3-base-risks.js` (вибір активу → `threatDirectory` → вибір загрози/вразливості →
  вибір впливу/ймовірності → попередній перегляд рівня → «Додати до переліку»), **плюс**:
  коли вибрано конкретну загрозу зі списку, авто-заповнюються (і стають нередагованими
  до збереження, як і зараз для impact/likelihood) `treatment_strategy`,
  `treatment_plan`, `responsible`, `control_refs`, `enhancement_suggestions`,
  `residual_risk` — копіюються з вихідного запису каталогу
  (`catalogs.threatsRisks.risks`, знайденого за збігом `threat`+`vulnerability`+
  `asset_id`, якщо такий є; якщо збігу нема через «усі загрози» — з першого запису, де
  збігається пара `threat`+`vulnerability`).
- **«Власна загроза»** (новий) — вільні текстові поля `Загроза` й `Вразливість`
  (замість селекту з довідника), вибір активу той самий. Немає полів
  впливу/ймовірності/стратегії в цьому режимі. Кнопка «Додати без оцінки» створює
  ризик через `buildCustomRisk` без `impact`/`likelihood` (`undefined`), решта полів —
  порожні рядки/дефолти. Одразу закриває модал і викликає `onSaved?.()`.

`presetAssetId` (переданий із Кроку 2) — підставляється в обидва режими як початкове
значення селекту активу; користувач може змінити на інший обраний актив.

`step3-base-risks.js` і `step2-assets.js` імпортують `openRiskFormModal` замість
дублювання логіки. Кнопка `+ Додати ризик` на Кроці 3 викликає
`openRiskFormModal({ onSaved: rerender })` без `presetAssetId` (як і зараз — вибір
активу порожній/перший).

## 3. Ризик без оцінки

`core/risk-engine.js`, `annotateRisk`:

```js
export function annotateRisk(risk, scale) {
  if (risk.impact == null || risk.likelihood == null) return { ...risk, score: null, level: null };
  const score = computeRiskScore(risk.impact, risk.likelihood);
  return { ...risk, score, level: riskLevel(score, scale) };
}
```

`buildCustomRisk` — без змін (уже приймає довільний `input`, просто `impact`/`likelihood`
можуть бути відсутні у викликах із режиму «Власна загроза»).

**Відображення в таблиці Кроку 3** (`step3-base-risks.js`, `customRows`): якщо
`r.level == null` — замість `<span class="badge lvl-…">` рендериться
`<span class="badge">Не оцінено</span>`; клітинки Вплив/Ймовірність — `—` замість
`String(r.impact)`/`` `${likelihood_label} / ${likelihood}` ``. Решта клітинок
(Стратегія/Заходи/Відповідальний/Залишковий) — як зараз, `cell-edit`-інпути з
порожніми значеннями (уже підтримується, бо ці поля й раніше могли бути порожніми
рядками).

**Редагування через модал `openEditCustomRiskModal`** (уже існує) — якщо `impact`/
`likelihood` не задані, селекти показують перший/порожній варіант; після збереження
(`saveCustomRiskEdit` → `annotateRisk`) ризик отримує реальний рівень, як тільки
користувач вибере обидва поля.

**risk-chips на Кроці 4** (`step6-verify.js`) — ризик без `level` просто не матиме
класу `lvl-…`; `riskChips()`/`lookup()` продовжують працювати за `control_refs`
(порожній масив у ризику без оцінки — вже так, chips не покажуться, це очікувано:
неоцінений ризик поки не привʼязаний до жодного контролю).

## 4. Дані каталогу для авто-заповнення

`threatDirectory(catalog, assetId)` (без змін) повертає лише `{threat, vulnerability}`.
Для авто-заповнення повного запису додається (в `risk-engine.js`):

```js
export function findCatalogRisk(catalog, assetId, threat, vulnerability) {
  return catalog.risks.find(r =>
    r.threat === threat && r.vulnerability === vulnerability &&
    (assetId ? r.asset_id === assetId : true)) ?? null;
}
```

Використовується у `risk-form.js` при виборі пункту в режимі «З переліку» — якщо
знайдено, копіюються всі поля крім `id`/`asset_id` (asset_id береться з обраного в
модалі активу, а не з вихідного запису, — той самий ризик може стосуватись кількох
активів через різні асети в довіднику).

## Валідація

- `npm test` — без регресій (жоден тест не покладається на автоматичне заповнення
  `accepted_base` при рендері Кроку 3, окрім тих, що самі задають `accepted_base`
  явно — вони не зачіпаються).
- Нові unit-тести на `annotateRisk` (без impact/likelihood → `level: null`) і на
  `findCatalogRisk`.
- Ручна перевірка: обрати актив на Кроці 2 → бачити перелік ризиків → зняти чекбокс
  на одному → перейти на Крок 3 → підтвердити, що знятий ризик відсутній у таблиці;
  додати «власну загрозу» через Крок 2 → перейти на Крок 3 → бачити рядок «Не оцінено»
  → відредагувати через модал → рівень зʼявляється.

## Поза межами цього дизайну

- Без зміни моделі `hidden_base`/`deleteBaseRisk` — видалення й далі незворотне й
  живе лише на Кроці 3.
- Без автоматичної валідації, що ризики без оцінки не потрапляють у фінальний
  DOCX-експорт «як є» — це поведінка «as-is» (експорт покаже порожні/«—» поля,
  так само, як показує таблиця).
