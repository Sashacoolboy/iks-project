# Assessment UI: 4 явних кроки оцінювання

**Дата:** 2026-08-21
**Статус:** Approved (доповнено 2026-08-21: чекбокси методів прибрані —
см. «Доповнення: без чекбоксів методів» в кінці файлу)

## Мета

Зробити явним для оцінювача, що оцінка пункту складається з 4 послідовних кроків:

1. **Валідність заповнення ЦПБ** — чи трактування параметра в ЦПБ відповідає вимозі НД ТЗІ
2. **Дослідження** (EXAMINE)
3. **Опитування** (INTERVIEW)
4. **Тестування** (TEST)

Це суто UX-переосмислення існуючого workflow. Модель даних оцінювання (`result` enum,
`methods_used`, `assessor_comment`, `conclusion`, evidence) **не змінюється** — змінюється
тільки те, як ці поля згруповані й підписані в інтерфейсі.

## Межі змін

- Без нових enum-значень, без нових полів у `results[]`.
- Один адитивний (non-breaking) виняток: нове поле `methods_reference` у plan items
  (нормативні тексти-підказки з адаптера — «що досліджувати / кого опитувати / що
  тестувати»), яке зараз існує в `data/assessment/assessment_odp_adapter.json` на рівні
  контролю, але не потрапляє в план і не показується в UI.

## 1. Дані: `methods_reference` у plan items

`core/assessment/assessment-plan.js`, `buildAssessmentPlan()`: для кожного item додається

```js
methods_reference: adapterCtrl?.assessment_methods_reference ?? {}
```

де `adapterCtrl` — вже наявна в коді змінна (`adapterIndex.controls.get(catCtrl.control_id)`).
Значення — об'єкт виду `{ EXAMINE: [text...], INTERVIEW: [text...], TEST: [text...] }`
(як у адаптері, ключі можуть бути відсутні, якщо в адаптері немає відповідного методу).

Поле адитивне — існуючі тести на точні значення items (`assessment-plan.test.js`) не
перевіряють повний об'єкт item через `deepEqual`, тож не ламаються.

## 2. Головна таблиця (`assessment-table.js`) — лише лейбли

- Заголовки колонок «Значення БПБ» / «Значення ЦПБ» отримують візуальний маркер кроку 1
  (напр. `<span class="step-badge">1</span>` перед текстом заголовка або підзаголовок
  «Крок 1: валідність ЦПБ» над парою колонок).
- Колонка «Вибір типів дослідження» (чекбокси методів) **видаляється повністю** —
  див. доповнення в кінці файлу.
- Ніякої іншої зміни в обробниках подій, стані чи структурі даних.

## 3. Деталь-панель (`assessment-item.js`) — 4 нумеровані секції

Поточний порядок секцій (шаблон мети → ODP-таблиця → коментар → висновок → докази →
findings → traceability) переробляється так:

1. **Секція "Крок 1. Валідність заповнення ЦПБ"**:
   - Текст вимоги НД ТЗІ (`planItem.statement_text`, вже доступний)
   - Таблиця значень ЦПБ/БПБ з джерелом (наявна `odpTable`, переноситься сюди)
   - Коротка статична підказка: «Перевірте, чи трактування параметра в ЦПБ відповідає
     вимозі НД ТЗІ»

2. **Секції "Крок 2. Дослідження" / "Крок 3. Опитування" / "Крок 4. Тестування"**:
   - Лише нормативний текст-підказка з `planItem.methods_reference[METHOD]` (join, якщо
     масив >1 рядка); якщо відсутній — коротка заглушка «Підказка відсутня для цього
     заходу». Секції інформаційні (read-only) — без чекбоксів, без запису в дані (див.
     доповнення нижче: `methods_used` більше ніде не встановлюється з UI).

Після 4 кроків — без змін: «Коментар оцінювача», «Висновок», evidence editor, findings,
traceability drawer (це підсумкові поля, що стосуються всіх 4 кроків одночасно, а не
одного конкретного).

## Тестування

- `test/assessment/assessment-plan.test.js`: новий тест — `methods_reference` присутній
  на item і відповідає адаптеру для контролю з відомими EXAMINE/INTERVIEW/TEST текстами.
- `test/assessment/assessment-table.test.js`: колонка методів більше не рендериться;
  `itemRow`/`renderAssessmentTable` не викликають `patchResult` з `methods_used`.
- Ручна e2e-перевірка в браузері: відкрити деталь-панель пункту, переконатись що 4 секції
  показуються по порядку, кроки 2-4 — суто текст-підказка без інтерактивних елементів.

## Поза межами цієї ітерації

- Без окремих result/висновку на кожен із 4 кроків (лишається один загальний `result` +
  один `conclusion` на пункт).

## Доповнення: без чекбоксів методів (2026-08-21)

**Причина:** оцінювач фактично описує застосовані методи (дослідження/опитування/
перевірка) у вільному тексті висновку — структурований чекбокс дублює цю інформацію
без користі. Рішення: **прибрати повністю** — таблицю, деталь-панель і DOCX-звіт.

**Що саме змінюється (понад початковий текст спеки вище):**

1. `public/js/assessment/assessment-table.js`:
   - Видалити блок `methodsDiv`/чекбокси в `itemRow` і відповідну колонку `<th>`
     («Вибір типів дослідження») в `thead`.
   - `patchResult` більше ніколи не викликається з `{ methods_used }`.
2. `public/js/assessment/assessment-item.js`: кроки 2-4 — лише текст `methods_reference`,
   без чекбоксів (як зафіксовано вище).
3. **Дані (`core/assessment/assessment-run.js`, `assessment-io.js`)**: поле `methods_used`
   **лишається в схемі результату** (не видаляється — уникаємо зміни валідатора й
   міграції v1→v3, які й далі можуть відновлювати `methods_used` зі старих
   `evidence[].method` записів). Просто жодна дія в v3 UI більше його не встановлює.
4. **DOCX-звіт видаляє метод-специфічний вміст повністю:**
   - `core/assessment/report-projection.js`: прибрати обчислення `methodCounts`/`methods`
     і поле `methods_used_labels` з кожного item-проекції.
   - `core/docx/assessment-docx-writer.js`: прибрати секцію «4. Методи оцінювання»
     (лічильники використання) і колонку «Методи» в таблиці розділу «Результати
     оцінювання за класами заходів захисту»; перенумерувати наступні секції (5→4,
     6→5 і т.д., звірити всі заголовки `par('N. …')` по файлу).
   - Оновити `test/assessment/report-projection.test.js` (без `methods`/
     `methods_used_labels` у очікуваному проекції) та
     `test/assessment/assessment-docx-writer.test.js` (без методів у вхідних даних
     фікстури й очікуваному тексті/номерах секцій).

**Не змінюється:** `updateResult`/`assessment-run.js` API (`methods_used` як ключ
patch — лишається валідним, просто непотрібним у новому UI); валідатор схеми
(`assessment-validator.js`, якщо перевіряє `methods_used` — не займати).
