# Assessment UI: документ-в'ю по контролю (НД ТЗІ ↔ фактичний ЦПБ)

**Дата:** 2026-08-21
**Статус:** Approved
**Продовжує:** [2026-08-21-assessment-ui-4-steps-design.md](./2026-08-21-assessment-ui-4-steps-design.md)

## Мета

Учорашня спека визначила «Крок 1: валідність заповнення ЦПБ» як окрему секцію в
деталь-панелі одного пункту. Ця спека додає **другий, вищий рівень огляду** — по
кожному **контролю** (AC-02, AU-11 тощо), а не по кожному окремому пункту оцінювання:
оцінювач бачить одразу весь захід захисту як цілісний документ у двох варіантах —
(1) як його сформулювала норма НД ТЗІ, і (2) як його фактично заповнено в ЦПБ,
з візуальною підсвіткою походження кожного значення.

Це не суперечить і не замінює «Крок 1» з учорашньої спеки (той лишається в
деталь-панелі окремого пункту) — це ширший контекст, що показується одразу для
всього контролю, перш ніж оцінювач починає оцінювати пункти/ODP окремо.

## Референс

У майстрі заповнення ЦПБ (Крок 6 «Верифікація», `public/js/steps/step6-verify.js`)
вже є ідентичний за духом механізм: рендер тексту заходу з інлайн-підсвіченими
параметрами, кольори за джерелом заповнення:

```css
.src-policy { background: #c6f6d5; }       /* зелений — зі словника політик (v1, у v3 немає) */
.src-bpb, .src-generic { background: #e2e8f0; }  /* сірий — успадковано з БПБ / типове значення */
.src-empty { background: #fed7d7; font-weight: 600; } /* червоний — не визначено */
.src-override { background: #bee3f8; }     /* синій — введено вручну в ЦПБ */
```

Ці ж класи (крім `.src-policy`, якого немає у v3-моделі) переносяться в модуль
оцінювання без змін CSS.

## Розміщення

Розгортається під заголовком групи контролю (`AC-02 — УПРАВЛІННЯ ОБЛІКОВИМИ
ЗАПИСАМИ`) у головній таблиці — по кліку на заголовок (той самий рядок, що зараз
просто статичний лейбл, отримує onclick + іконку згорнути/розгорнути, за замовчуванням
згорнутий). Розгорнутий стан — над таблицею per-ODP/per-item рядків цього контролю.

## Дані (без змін бекенду)

Усе необхідне вже є в plan items:
- `statement_text` на кожному STATEMENT-kind item — це **сирий** текст пункту з
  nd_tzi, включно з `{{ insert: param, LOCAL_ODP_ID }}` (плейсхолдери не
  розв'язані — це вже підтверджено роботою над AU-11/IR-8 раніше сьогодні)
- `statement_path` — для визначення мітки пункту (a, b, c…), тим самим механізмом,
  що вже використовує `firstSegmentLabel`/`statementTitle` у `assessment-table.js`
- `odp_values` — на кожному item контролю це **той самий** повний масив (усі
  assessment_odps контролю, `assessment-plan.js` призначає його ідентично всім
  items одного контролю) з `local_odp_id`, `target_value`, `effective_source`
- `kind` — фільтр: у документ-в'ю потрапляють лише `STATEMENT`-рядки (реальні
  пункти a/b/c… заходу); `ODP_DEFINITION`-рядки (синтетичні ODP-визначення)
  лишаються тільки в існуючій per-ODP таблиці нижче

## Побудова (нова чиста функція, тестована без DOM)

Новий модуль `public/js/assessment/control-document-view.js`:

```js
export function buildControlDocument(items) // items: controlGroup.items (пари {planItem, result})
// -> { left: LineParts[], right: LineParts[] }
// LineParts = { label: string, parts: Array<{ type: 'text', text } | { type: 'param', text, source }> }
```

Алгоритм:
1. Фільтрувати `items` за `planItem.kind === 'STATEMENT'`, зберігаючи порядок.
2. Для кожного item побудувати мапу `local_odp_id → { value, effective_source }`
   з `planItem.odp_values` (once — масив однаковий для всіх items контролю, можна
   взяти з першого item).
3. Розібрати `statement_text` регуляркою (та сама, що в `collapsePlaceholders`:
   `/\{\{\s*insert:\s*param,\s*([\w.-]+)\s*\}\}/g`) на послідовність
   text/param-частин.
4. **Ліва колонка**: параметр-частини рендеряться як `[local_odp_id]` (як зараз
   у тултіпах, без кольору) — це «трактування норми».
5. **Права колонка**: параметр-частини рендеряться як фактичне значення з мапи
   (`formatOdpValue(target_value)` або `'не визначено'`, якщо
   `effective_source` відсутній/UNRESOLVED), з класом `src-override` /
   `src-bpb` / `src-generic` / `src-empty` відповідно до `effective_source`
   (`CPB_OVERRIDE`→`src-override`, `BPB_INHERITED`→`src-bpb`,
   `GENERIC_DEFAULT`→`src-generic`, інакше→`src-empty`).
6. Мітка рядка (`label`) — перший сегмент `statement_path` (той самий
   `firstSegmentLabel`, що вже експортується/використовується в
   `assessment-table.js`; винести у спільний невеликий утиліт-файл або
   реекспортувати).

## Рендер (DOM)

`renderControlDocument(container, items)` — рендерить:
- Легенду кольорів один раз зверху блоку: «синій — введено вручну в ЦПБ; сірий —
  успадковано з БПБ/типове значення; червоний — не визначено»
- Дві колонки (`<div class="control-doc-columns">` з двома `<div>` всередині, або
  `<table>` із двома `<td>`) — ліва «Трактування з НД ТЗІ», права «Фактичний
  ЦПБ», кожна — список `<p>` рядків з міткою (`a.`, `b.`…) і inline `<span>` для
  параметрів.

## Інтеграція в `assessment-table.js`

- Заголовок групи контролю (`group-row control`) отримує:
  - toggle-стан (новий `Set` на модульному рівні, аналогічно `expandedRows`, або
    розширення того ж стану новим namespace, напр. `expandedControlDocs`)
  - клікабельність (onclick перемикає стан, rerender)
  - невелику іконку/стрілку, що показує згорнуто/розгорнуто
- Якщо розгорнуто — між рядком заголовка контролю і першим item-рядком
  вставляється `<tr><td colspan="8">` з результатом `renderControlDocument`.

## Тестування

- `test/assessment/control-document-view.test.js`: unit-тести `buildControlDocument`
  на фікстурі controlGroup.items (2-3 STATEMENT items з різними
  `effective_source`, один UNRESOLVED) — перевірка обох колонок, підпис міток,
  фільтрація ODP_DEFINITION-рядків.
- Ручна e2e-перевірка в браузері: розгорнути AC-02, переконатись що обидві
  колонки показуються, кольори відповідають джерелам, клік згортає назад.

## Поза межами цієї ітерації

- Без агрегованого огляду на рівні сім'ї (AC) — тільки на рівні контролю (AC-02),
  за рішенням користувача.
- Без редагування значень прямо в цьому блоці (це read-only контекст; редагування
  значень ЦПБ відбувається в майстрі ЦПБ, не в модулі оцінювання).
- Без експорту цього блоку в DOCX-звіт у цій ітерації.
