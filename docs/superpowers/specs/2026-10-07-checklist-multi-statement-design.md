# Design: Множинні стейтменти перевірки на захід захисту (редагування через модальне вікно)

**Дата:** 2026-10-07
**Статус:** затверджено користувачем, до впровадження
**Передумова:** [2026-10-06-assessment-plan-checklist-design.md](./2026-10-06-assessment-plan-checklist-design.md) (погоджено та злито в master)

## 1. Мета

Попередня реалізація чекліста зберігала **один** текст інструкції перевірки
(`verification_statement: string|null`) на кожен захід/посилення, редагований
через інлайн-`<textarea>` прямо в рядку списку.

На практиці один захід захисту часто потребує кількох незалежних пунктів
перевірки (наприклад: «Перевірити журнал ведення облікових записів»,
«Перевірити журнал оновлення паролів», «Перевірити якість шифрування паролів
та довжину паролів» — три окремі дії в межах одного заходу). Потрібно:
1. Замінити одне поле на **масив стейтментів**.
2. Показувати кожен стейтмент як текст (read-only) з кнопками
   «Редагувати»/«Видалити» біля нього.
3. Редагування відбувається в модальному вікні (не інлайн), з плейсхолдером,
   якщо текст відсутній.
4. Додати кнопку «Додати пункт перевірки» на кожен захід/посилення — відкриває
   модалку для введення нового стейтмента.

## 2. Модель даних

### 2.1 `plan.checklist[]` — зміна форми запису
Було:
```json
{ "control_id": "AT-02", "verification_statement": "текст або null", "source_status": "GENERATED" }
```
Стає:
```json
{
  "control_id": "AT-02",
  "statements": [
    { "id": "AT-2#1", "text": "Перевірити журнал ведення облікових записів…" },
    { "id": "AT-2#2", "text": "Перевірити журнал оновлення паролів…" }
  ]
}
```
- Поле `source_status` **видаляється** — весь UI/плейсхолдер-стан тепер
  визначається напряму через `statements.length === 0`.
- `verification_statement` **видаляється**.
- `id` згенерованих (з довідника) стейтментів — детермінований:
  `${canonical_control_id}#${1-based index}` (напр. `AT-2#1`, `AT-2#2`).
  Це зберігає відтворюваність `buildAssessmentPlan` у тестах.
- `id` стейтментів, доданих оцінювачем уручну через кнопку «Додати пункт
  перевірки», — `crypto.randomUUID()` (стандартний Web Crypto API в браузері,
  без нової npm-залежності).
- `included`/`exclusion_reason` на рівні заходу (не стейтмента) — без змін.

### 2.2 `data/assessment/checklist_reference.json` — зміна форми довідника
Було: `"verification_statement": "один суцільний текст з {{ insert: param, ... }}"`.
Стає: `"statements": ["перший пункт з {{ insert: param, ... }}", "другий пункт", ...]`
— масив окремих рядків-шаблонів (кожен — самостійний пункт перевірки, той
самий синтаксис плейсхолдерів).

Пілотний контент родини AT (15 записів, затверджений
[2026-10-06](./2026-10-06-assessment-plan-checklist-design.md)) **переписується
на цей новий формат**: кожен існуючий суцільний текст розбивається на окремі
природні пункти перевірки (за зразком вашого прикладу — один пункт на одну
конкретну дію/артефакт перевірки, а не один абзац на весь захід). Контент
переписується разом із реалізацією цього дизайну (Task 1 плану реалізації), не
окремим довідниковим проходом.

## 3. Побудова плану (`core/assessment/assessment-plan.js`)

Резолвер (`core/assessment/checklist-resolver.js`) **не змінюється** — він і
зараз резолвить один рядок-шаблон за раз
(`resolveChecklistStatement({ template, effectiveValueFor })`).

У циклі побудови чекліста (`buildAssessmentPlan`):
- якщо є довідникова стаття (`checklistEntries[canonicalId]`) — для кожного
  рядка `refEntry.statements[i]` викликати `resolveChecklistStatement`,
  зібрати `statements: refEntry.statements.map((tpl, i) => ({ id:
  `${canonicalId}#${i+1}`, text: resolveChecklistStatement({ template: tpl,
  effectiveValueFor }).resolved_statement }))`;
- якщо статті нема — `statements: []` (без жодного запису-заглушки; порожній
  масив — весь сигнал «треба заповнити вручну», який UI показує як плейсхолдер
  + кнопку додавання, а не окремий прапорець).

## 4. UI (`public/js/assessment/plan-review.js`)

На кожному заході (без змін: чекбокс «включити в оцінювання» на рівні заходу):
- Список стейтментів: кожен — текст (read-only, `el('p', ...)` чи подібне) +
  кнопка **Редагувати** + кнопка **Видалити** (клас `.link-btn`, за зразком
  `step3-base-risks.js`).
- Якщо `statements.length === 0` — рядок-плейсхолдер «Немає пунктів перевірки
  — додайте власний».
- Кнопка **+ Додати пункт перевірки** під списком стейтментів заходу —
  відкриває модалку (`showModal` з `public/js/render/dom.js`, той самий
  компонент, що й у формі ризиків/загроз) з `<textarea>` (порожня) + кнопки
  «Зберегти»/«Скасувати». Зберегти — додає новий стейтмент
  (`{ id: crypto.randomUUID(), text }`) у масив заходу, закриває модалку.
- Кнопка **Редагувати** на існуючому стейтменті — та сама модалка, попередньо
  заповнена поточним текстом, + кнопка «Видалити» (з `confirm(...)`, за
  зразком `step3-base-risks.js`). Зберегти — оновлює текст цього стейтмента за
  `id`; Видалити — прибирає стейтмент з масиву.
- Увесь запис оцінювання зберігається, як і зараз, через існуючий
  `setAssessment`-дебаунс (без ручної кнопки збереження для всього екрана —
  зміни в модалці застосовуються одразу при «Зберегти»/«Видалити»).

## 5. Експорт і виконання

### 5.1 `core/assessment/checklist-projection.js` / `core/docx/checklist-docx-writer.js`
Комірка «Інструкція перевірки» об'єднує всі `statements[].text`, по одному
пункту на рядок, із нумерацією для читабельності:
```
1. Перевірити журнал ведення облікових записів…
2. Перевірити журнал оновлення паролів…
```
(`cell()` у `docx-writer.js` уже розбиває вміст по `\n` на окремі параграфи —
досить об'єднати нумеровані рядки через `\n`.) Якщо `statements.length === 0`
— та сама заглушка `[немає згенерованої інструкції — заповніть вручну]`, що й
зараз.

### 5.2 `public/js/assessment/assessment-table.js` (контекст над пунктами виконання)
Замість одного рядка `<em>` — список: один `<em>`/рядок на стейтмент (ті самі
нумеровані пункти, що й у DOCX, для візуальної узгодженості). Порожній масив —
нічого не рендериться (як і зараз для `null`).

## 6. Сумісність

Наявний тестовий запис `ASSESS-2026-1026` (створений під час ручної
перевірки, старий формат `verification_statement`) — **видаляється**, міграція
не потрібна (підтверджено користувачем).

Для стійкості на майбутнє (якщо колись з'явиться запис зі старим полем) —
легка нормалізація додається в `migrateAssessment`
(`core/assessment/assessment-io.js`): якщо запис чекліста має рядкове поле
`verification_statement` (старий формат) і не має `statements` — конвертувати
в `statements: [{ id: `${control_id}#1`, text: verification_statement }]`
(якщо рядок непорожній) або `[]` (якщо `null`/порожній), і видалити старі поля
`verification_statement`/`source_status`. Той самий патерн backfill, що й уже
існує для `plan.checklist` загалом.

## 7. Нефункціональні обмеження (без змін)
- Zero npm dependencies — `crypto.randomUUID()` це стандартний Web API, не
  пакет.
- UI рендериться лише через `el()`/textContent — без `innerHTML`.
- DOCX-вивід відтворюваний (дати з `projection.title.date`, без поточного
  часу).
